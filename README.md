# Document Intelligence API

## What it does

A FastAPI service that turns PDFs and Word documents into a queryable knowledge base. Upload a document and it's automatically extracted, chunked, embedded, and indexed in Postgres with `pgvector`. Then ask questions in natural language across one or many uploaded documents, and get back an LLM-generated answer with exact page-level citations for every source it used.

## Features

- **Automatic ingestion** — upload a PDF or Word (`.docx`) file and it's parsed, split into overlapping chunks, embedded, and stored in one request.
- **Page-aware chunking** — PDF chunks keep a reference to the page they came from, so answers can cite exactly where they came from. (Word files have no real page numbers to attribute — see [Known limitations](#known-limitations).)
- **Semantic search** — questions are embedded with the same model as the documents and matched with `pgvector` cosine similarity, so retrieval works on meaning, not keywords.
- **Multi-document Q&A** — search across every uploaded document, or scope a question to a specific set of filenames.
- **Local, private inference** — answers are generated by a locally-running Ollama model, so no document content leaves your machine.
- **Grounded answers** — the LLM is instructed to answer only from retrieved context and to say so when it can't find an answer, rather than guessing.

## Setup & Installation

### Prerequisites

- Python 3.12+
- [uv](https://docs.astral.sh/uv/) (used for dependency management — `pip` works too)
- PostgreSQL with the [`pgvector`](https://github.com/pgvector/pgvector) extension available
- [Ollama](https://ollama.com/) installed and running locally

### Clone the repo

```bash
git clone https://github.com/IrhaNaveed/Document-Intelligence-API.git
cd Document-Intelligence-API
```

### Install dependencies

```bash
uv sync
```

### Pull an LLM for Ollama

```bash
ollama pull llama3.2
```

### Set up `.env`

Create a `.env` file in the project root:

```env
DB_URL=postgresql+asyncpg://<user>:<password>@localhost:5432/<database>
EMBEDDING_DIM=384
OLLAMA_MODEL=llama3.2
OLLAMA_BASE_URL=http://localhost:11434
```

- `DB_URL` — async SQLAlchemy connection string for your Postgres instance.
- `EMBEDDING_DIM` — must match the output dimension of the embedding model (`all-MiniLM-L6-v2` = 384).
- `OLLAMA_MODEL` / `OLLAMA_BASE_URL` — optional; default to `llama3.2` and `http://localhost:11434` if omitted.

The `vector` extension and the `chunks` table are created automatically on startup — no manual migration needed.

### Run the app

```bash
uv run uvicorn main:app --reload
```

The API is now available at `http://localhost:8000`, with interactive docs at `http://localhost:8000/docs`.

## API Endpoints

### `GET /`

Health check.

```bash
curl http://localhost:8000/
```
```json
{"message": "Working"}
```

### `POST /api/fileUpload`

Upload a document. It's extracted, chunked, embedded, and stored.

```bash
curl -X POST http://localhost:8000/api/fileUpload \
  -F "file=@invoice.pdf"
```
```json
"invoice.pdf"
```

Supported extensions: `pdf`, `docx`. Legacy `.doc` files are rejected with a `415` asking for a `.docx` or PDF conversion — see [Known limitations](#known-limitations).

### `POST /api/ask`

Ask a question over the indexed documents.

```bash
curl -X POST http://localhost:8000/api/ask \
  -H "Content-Type: application/json" \
  -d '{
        "question": "What is the invoice total?",
        "document_names": ["invoice.pdf"],
        "top_k": 5
      }'
```

| Field | Type | Required | Description |
|---|---|---|---|
| `question` | string | yes | The question to answer |
| `document_names` | list of strings | no | Restrict the search to these filenames; omit to search everything |
| `top_k` | integer (1–20) | no | Number of chunks to retrieve as context (default `5`) |

```json
{
  "answer": "The invoice total is $500 [invoice.pdf, page 1].",
  "sources": [
    {
      "document": "invoice.pdf",
      "page": 1,
      "content": "The invoice total is 500 dollars.",
      "score": 0.823
    }
  ]
}
```

## How it works

**Ingestion.** The uploaded file is routed by extension. For PDFs, `pymupdf4llm` extracts each page as Markdown, keeping page boundaries intact, and each page is independently split with LangChain's `RecursiveCharacterTextSplitter` (1000-character chunks, 200-character overlap), so every resulting chunk still knows exactly which page it came from. For `.docx` files, `python-docx` extracts paragraph and table text (Word has no page numbers stored in the file itself — pagination is computed by the renderer — so these chunks carry no page number), and the same splitter is applied to the full text. Each chunk is embedded with `sentence-transformers/all-MiniLM-L6-v2` (384-dimensional vectors) and stored in a Postgres `chunks` table alongside its source filename and page number (when known), using `pgvector`'s HNSW index for fast approximate nearest-neighbor search.

**Retrieval.** When a question comes in, it's embedded with the same model used for the documents, so the question and the chunks live in the same vector space. `pgvector`'s cosine-distance operator ranks every chunk (optionally filtered to specific documents) by similarity to the question, and the top `k` are retrieved.

**Generation.** The retrieved chunks are assembled into a prompt, each one labelled with its `[document, page]` origin. A locally-running Ollama model (via `langchain-ollama`) is instructed to answer strictly from that context, citing sources in the same format, and to say it couldn't find an answer rather than fabricate one. The final response returns both the generated answer and the structured list of source chunks it was grounded in.

## Known limitations

- Legacy `.doc` files (the old binary Word format) aren't parsed — only `.docx` and PDF are supported. Convert `.doc` files to `.docx` or PDF before uploading.
- `.docx` chunks have no page number, since Word doesn't store pagination in the file (it's computed by the renderer at display/print time). Their citations include the document name only.
