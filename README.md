# Document Intelligence API

## What it does

A full-stack app that turns PDFs, Word documents, and Excel spreadsheets into a queryable knowledge base. Create an account, upload documents, and ask questions about them in natural language — a FastAPI backend extracts, chunks, embeds, and indexes each file in Postgres with `pgvector`, then answers questions with an LLM-generated response grounded in exact page-level citations (where the file format has pages). Every user's documents and chat history are private to their account. A React frontend (`document_agent/`) provides login/registration, a ChatGPT-style chat with conversation history, and a document upload/management view.

## Features

- **Accounts & per-user isolation** — JWT-based email/password auth. Every uploaded document and every conversation belongs to one account and is invisible to everyone else.
- **Automatic ingestion** — upload a PDF, Word (`.docx`), or Excel (`.xlsx`) file and it's parsed, split into overlapping chunks, embedded, and stored in one request. Excel sheets are extracted row by row (formula cells use their last-calculated value), grouped under a `## Sheet: <name>` heading per sheet.
- **Page-aware chunking** — PDF chunks keep a reference to the page they came from, so answers can cite exactly where they came from. (Word and Excel files have no real page numbers to attribute — see [Known limitations](#known-limitations).)
- **Hybrid search** — every question runs two searches: semantic (`pgvector` cosine similarity on embeddings, so it works on meaning) and keyword (Postgres full-text search, so exact terms like names, IDs, and acronyms are not missed). The two result lists are merged with Reciprocal Rank Fusion.
- **Cross-encoder reranking** — hybrid search fetches a wider candidate pool, then a cross-encoder re-scores each chunk against the question so the most relevant ones reach the LLM.
- **Multi-document Q&A** — search across every uploaded document, or scope a question to a specific set of filenames.
- **Streaming answers** — `POST /api/ask/stream` sends the answer token by token as Server-Sent Events, so clients can show text as it is generated instead of waiting for the whole response.
- **Persisted conversation history** — every question and answer (plus its sources) is saved to a conversation, so past chats can be listed and reopened later, exactly like the React frontend's "previous chats" sidebar does.
- **Local, private inference** — answers are generated by a locally-running Ollama model, so no document content leaves your machine.
- **Grounded answers** — the LLM is instructed to answer only from retrieved context and to say so when it can't find an answer, rather than guessing.
- **React frontend** — login/registration, a chat UI with streaming responses and a document-scope filter, a conversation history sidebar, and a document upload/list view. See [Frontend](#frontend-document_agent).

## Architecture

```
                 ┌──────────────────┐
  PDF upload ──▶ │  POST /api/       │
                 │  fileUpload       │
                 └────────┬─────────┘
                          │
             ┌────────────▼─────────────┐
             │ pymupdf4llm: extract text │
             │ per page (Markdown)       │
             └────────────┬─────────────┘
                          │
             ┌────────────▼─────────────┐
             │ LangChain text splitter   │
             │ (1000 chars, 200 overlap) │
             └────────────┬─────────────┘
                          │
             ┌────────────▼─────────────┐
             │ sentence-transformers     │
             │ all-MiniLM-L6-v2 embed    │
             └────────────┬─────────────┘
                          │
                          ▼
                ┌────────────────────┐
                │ Postgres + pgvector │◀── HNSW index (cosine)
                │  "chunks" table     │◀── GIN index (full-text)
                └─────────┬──────────┘
                          ▲
                          │ hybrid search (top_k x 4 candidates)
                          │   vector (cosine) + keyword (full-text)
                          │   merged with Reciprocal Rank Fusion
                          │
                 ┌────────┴─────────┐
   Question ───▶ │  POST /api/ask   │
                 └────────┬─────────┘
                          │
             ┌────────────▼─────────────┐
             │ cross-encoder reranker    │
             │ keeps the best top_k      │
             └────────────┬─────────────┘
                          │
             ┌────────────▼─────────────┐
             │ Ollama LLM (LangChain)    │
             │ answers from context only │
             └────────────┬─────────────┘
                          │
                          ▼
              Answer + [document, page] sources
                          │
                          ▼
          saved as a Message on the Conversation
```

Every route except `POST /api/auth/register` and `POST /api/auth/login` requires a JWT `Authorization: Bearer <token>` header (diagram omits this for clarity), and every query above is scoped to `owner_id = current_user.id` — one account never sees another account's chunks, documents, or conversations.

## Setup & Installation

### Prerequisites

- Python 3.12+
- [uv](https://docs.astral.sh/uv/) (used for dependency management — `pip` works too)
- PostgreSQL with the [`pgvector`](https://github.com/pgvector/pgvector) extension available
- [Ollama](https://ollama.com/) installed and running locally
- Node.js 18+ (only needed for the React frontend)

### Clone the repo

```bash
git clone https://github.com/IrhaNaveed/Document-Intelligence-API.git
cd Document-Intelligence-API
```

### Backend

#### Install dependencies

```bash
uv sync
```

#### Pull an LLM for Ollama

```bash
ollama pull llama3.2
```

#### Set up `.env`

Create a `.env` file in the project root:

```env
DB_URL=postgresql+asyncpg://<user>:<password>@localhost:5432/<database>
EMBEDDING_DIM=384
OLLAMA_MODEL=llama3.2
OLLAMA_BASE_URL=http://localhost:11434
RERANKER_MODEL=cross-encoder/ms-marco-MiniLM-L-6-v2
JWT_SECRET_KEY=change-me-to-a-long-random-string
JWT_EXPIRE_MINUTES=60
```

- `DB_URL` — async SQLAlchemy connection string for your Postgres instance.
- `EMBEDDING_DIM` — must match the output dimension of the embedding model (`all-MiniLM-L6-v2` = 384).
- `OLLAMA_MODEL` / `OLLAMA_BASE_URL` — optional; default to `llama3.2` and `http://localhost:11434` if omitted.
- `RERANKER_MODEL` — optional; the cross-encoder used to rerank retrieved chunks. Defaults to `cross-encoder/ms-marco-MiniLM-L-6-v2` (downloaded from Hugging Face on first run).
- `JWT_SECRET_KEY` — **required**; the app fails to start without it. Used to sign access tokens — use a long random string, and never commit a real one.
- `JWT_EXPIRE_MINUTES` — optional; how long an access token stays valid (default `60`).

The `vector` extension and every table (`users`, `chunks`, `conversations`, `messages`) plus their indexes are created automatically on startup — no manual migration needed, including for databases created before hybrid search or conversation history existed.

#### Run the app

```bash
uv run uvicorn main:app --reload
```

The API is now available at `http://localhost:8000`, with interactive docs at `http://localhost:8000/docs`.

> The backend's CORS policy only allows requests from `http://localhost:5173` (the frontend's dev server origin) — see `main.py` if you need to allow another origin.

### Frontend setup

```bash
cd document_agent
npm install
cp .env.example .env   # VITE_API_BASE_URL=http://localhost:8000
npm run dev
```

The app is now available at `http://localhost:5173`. See [Frontend](#frontend-document_agent) below for what it does.

## API Endpoints

### `GET /`

Health check.

```bash
curl http://localhost:8000/
```
```json
{"message": "Working"}
```

### Authentication

Every other endpoint requires the header `Authorization: Bearer <access_token>`, obtained from `/api/auth/login`.

#### `POST /api/auth/register`

```bash
curl -X POST http://localhost:8000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email": "you@example.com", "password": "a-long-password"}'
```
```json
{"id": 1, "email": "you@example.com"}
```

Password must be at least 8 characters. Returns `400` if the email is already registered.

#### `POST /api/auth/login`

Standard OAuth2 password flow — the body is `application/x-www-form-urlencoded`, with the email in the `username` field.

```bash
curl -X POST http://localhost:8000/api/auth/login \
  -d "username=you@example.com&password=a-long-password"
```
```json
{"access_token": "<jwt>", "token_type": "bearer"}
```

#### `GET /api/auth/me`

Returns the current user for the given token.

```bash
curl http://localhost:8000/api/auth/me \
  -H "Authorization: Bearer <access_token>"
```
```json
{"id": 1, "email": "you@example.com"}
```

### `POST /api/fileUpload`

Upload a document. It's extracted, chunked, embedded, and stored under the authenticated user.

```bash
curl -X POST http://localhost:8000/api/fileUpload \
  -H "Authorization: Bearer <access_token>" \
  -F "file=@invoice.pdf"
```
```json
"invoice.pdf"
```

Supported extensions: `pdf`, `docx`, `xlsx`. Legacy `.doc` and `.xls` files are rejected — see [Known limitations](#known-limitations). Re-uploading a file with the same name replaces its previously stored chunks.

### `GET /api/documents`

Lists the current user's uploaded documents, grouped from their stored chunks.

```bash
curl http://localhost:8000/api/documents \
  -H "Authorization: Bearer <access_token>"
```
```json
[
  {"document_name": "invoice.pdf", "chunk_count": 4, "uploaded_at": "2026-09-27T12:00:00Z"}
]
```

### `DELETE /api/documents/{document_name}`

Deletes every stored chunk for that document name under the current user (URL-encode the filename if it contains spaces or special characters).

```bash
curl -X DELETE "http://localhost:8000/api/documents/invoice.pdf" \
  -H "Authorization: Bearer <access_token>"
```

Returns `204 No Content`, or `404` if no document with that name exists for the current user.

### `POST /api/ask`

Ask a question over the indexed documents. Every question/answer exchange is saved to the given conversation — see [Conversations](#conversations) for how to create one first.

```bash
curl -X POST http://localhost:8000/api/ask \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{
        "question": "What is the invoice total?",
        "conversation_id": 1,
        "document_names": ["invoice.pdf"],
        "top_k": 5
      }'
```

| Field | Type | Required | Description |
|---|---|---|---|
| `question` | string | yes | The question to answer |
| `conversation_id` | integer | yes | Conversation this exchange is saved to — create one with `POST /api/conversations` first |
| `document_names` | list of strings | no | Restrict the search to these filenames; omit to search everything |
| `top_k` | integer (1–20) | no | Number of chunks passed to the LLM as context after reranking (default `5`) |

```json
{
  "answer": "The invoice total is $500 [invoice.pdf, page 1].",
  "sources": [
    {
      "document": "invoice.pdf",
      "page": 1,
      "content": "The invoice total is 500 dollars.",
      "score": 0.9931
    }
  ]
}
```

### `POST /api/ask/stream`

Same request body as `/api/ask`, but the answer arrives incrementally as [Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events). Use `-N` with curl so it doesn't buffer the output. The exchange is persisted to the conversation once the stream finishes.

```bash
curl -N -X POST http://localhost:8000/api/ask/stream \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"question": "What is the invoice total?", "conversation_id": 1, "top_k": 5}'
```
```
event: sources
data: [{"document": "invoice.pdf", "page": 1, "content": "...", "score": 0.9931}]

event: token
data: "The"

event: token
data: " invoice"

...

event: done
data: {}
```

| Event | Data | Meaning |
|---|---|---|
| `sources` | list of sources | Sent first, before generation starts — retrieval is already finished |
| `token` | string | One piece of the answer; concatenate them in order |
| `done` | `{}` | The answer is complete (and has been saved) |
| `error` | `{"detail": "..."}` | Ollama failed partway through the answer (sent instead of `done`) |

Each `data:` payload is JSON, so tokens containing newlines or quotes are safe to parse with `JSON.parse`. If Ollama can't be reached at all, the endpoint returns a normal `503` (or `502`) before streaming starts, the same as `/api/ask`. Note that `EventSource` can't be used to call this endpoint directly, since it needs a POST body and an `Authorization` header — see the frontend's `streamAsk` helper for a `fetch`-based SSE reader.

### Conversations

A conversation groups a sequence of question/answer exchanges, like a chat thread. Only the owner can read, extend, or delete their own conversations (`404` otherwise).

#### `POST /api/conversations`

Creates an empty conversation titled `"New conversation"`. Its title is automatically replaced with the first question once an exchange is asked against it.

```bash
curl -X POST http://localhost:8000/api/conversations \
  -H "Authorization: Bearer <access_token>"
```
```json
{"id": 1, "title": "New conversation", "created_at": "...", "updated_at": "..."}
```

#### `GET /api/conversations`

Lists the current user's conversations, most recently updated first.

```bash
curl http://localhost:8000/api/conversations \
  -H "Authorization: Bearer <access_token>"
```
```json
[{"id": 1, "title": "What is the invoice total?", "created_at": "...", "updated_at": "..."}]
```

#### `GET /api/conversations/{conversation_id}`

Returns a conversation with its full message history, in order.

```bash
curl http://localhost:8000/api/conversations/1 \
  -H "Authorization: Bearer <access_token>"
```
```json
{
  "id": 1,
  "title": "What is the invoice total?",
  "created_at": "...",
  "updated_at": "...",
  "messages": [
    {"id": 1, "role": "user", "content": "What is the invoice total?", "sources": null, "created_at": "..."},
    {"id": 2, "role": "assistant", "content": "The invoice total is $500 [invoice.pdf, page 1].", "sources": [{"document": "invoice.pdf", "page": 1, "content": "...", "score": 0.9931}], "created_at": "..."}
  ]
}
```

#### `DELETE /api/conversations/{conversation_id}`

Deletes a conversation and all of its messages.

```bash
curl -X DELETE http://localhost:8000/api/conversations/1 \
  -H "Authorization: Bearer <access_token>"
```

Returns `204 No Content`.

## How it works

**Auth.** Registration hashes the password with `bcrypt` and stores the user; login verifies it and returns a JWT signed with `JWT_SECRET_KEY`, embedding the user's id as `sub` with an expiry. Every other endpoint decodes that token via a FastAPI dependency to resolve the current user, and every query is filtered by that user's id, so accounts are fully isolated from each other.

**Ingestion.** The uploaded file is routed by extension. For PDFs, `pymupdf4llm` extracts each page as Markdown, keeping page boundaries intact, and each page is independently split with LangChain's `RecursiveCharacterTextSplitter` (1000-character chunks, 200-character overlap), so every resulting chunk still knows exactly which page it came from. For `.docx` files, `python-docx` extracts paragraph and table text (Word has no page numbers stored in the file itself — pagination is computed by the renderer — so these chunks carry no page number), and the same splitter is applied to the full text. For `.xlsx` files, `openpyxl` reads every sheet's cells (using each formula's last-cached computed value rather than the formula string), joins each row with `|`, and prefixes each sheet with a `## Sheet: <name>` heading before the same splitter is applied — Excel has no page concept, so these chunks also carry no page number. Each chunk is embedded with `sentence-transformers/all-MiniLM-L6-v2` (384-dimensional vectors) and stored in a Postgres `chunks` table alongside its source filename, owner, and page number (when known), using `pgvector`'s HNSW index for fast approximate nearest-neighbor search.

**Retrieval.** Each question goes through three stages, always scoped to the requesting user's own chunks. First, two searches run over the same chunks (optionally filtered to specific documents): a semantic search, where the question is embedded with the same model used for the documents and `pgvector`'s cosine-distance operator ranks chunks by meaning, and a keyword search, where Postgres full-text search (a generated `tsvector` column with a GIN index) ranks chunks by how many of the question's terms they contain, matching any term rather than requiring all of them. Each search returns its top `4 × k`. Second, the two ranked lists are merged with Reciprocal Rank Fusion, which scores each chunk by `1 / (60 + rank)` in every list it appears in, so chunks that both searches like rise to the top without having to compare cosine distances against full-text scores. Third, a cross-encoder (`cross-encoder/ms-marco-MiniLM-L-6-v2`) reads the question and each merged candidate together and re-scores them, which is slower but far more accurate than comparing embeddings; the best `k` after reranking become the LLM's context. The `score` returned with each source is this reranker relevance (0–1).

**Generation.** (Streaming works the same way, except the answer is emitted as the model produces it and the sources are sent first.) The retrieved chunks are assembled into a prompt, each one labelled with its `[document, page]` origin. A locally-running Ollama model (via `langchain-ollama`) is instructed to answer strictly from that context, citing sources in the same format, and to say it couldn't find an answer rather than fabricate one. The final response returns both the generated answer and the structured list of source chunks it was grounded in.

**Persistence.** Once an answer is fully generated, the question and answer (with its sources) are saved as two `Message` rows on the given `Conversation`, and the conversation's `updated_at` is bumped so it sorts to the top of the conversation list. The first exchange also sets the conversation's title from the question text. For `/ask/stream`, this happens after the SSE stream finishes, using a separate database session so it isn't tied to the lifetime of the request that opened the stream.

## Frontend (`document_agent/`)

A Vite + React 19 app that consumes the API above.

- **Auth pages** — `/login` and `/register`, backed by `react-hook-form` + `zod` validation. A successful login/register stores the JWT and redirects into the app; a valid token is required to reach anything else.
- **Chat** (`/chat`) — ask questions and watch the answer stream in token-by-token via `/api/ask/stream`, with a collapsible list of cited sources under each answer and an optional filter to scope a question to specific documents. A sidebar lists previous conversations (title, last-updated date), lets you switch between them (reloading that conversation's saved history from `GET /api/conversations/:id`), start a new one, or delete one. A new conversation is only created in the backend once you actually send a message, so browsing never leaves empty conversations behind. Switching conversations or starting a new one is disabled while a response is still streaming, since the exchange isn't saved yet.
- **Documents** (`/documents`) — lists uploaded documents (name, chunk count, upload date) via `GET /api/documents`, a button to upload a new PDF, DOCX, or XLSX file, and a delete button (revealed on hover) that removes a document and all of its chunks via `DELETE /api/documents/{document_name}`.

**State management is split by what it represents:**
- **Redux Toolkit** (`src/features/*/*.js`) holds client-side session state: the auth token/current user, and the active conversation's messages (including in-progress streaming tokens).
- **TanStack Query** (`src/features/documents/documentsHooks.js`, `src/features/conversations/conversationsHooks.js`) holds server state: the documents list and the conversations list, with mutations that invalidate the relevant query on success (e.g. uploading a document refreshes the document list).

Chat streaming is implemented with a hand-rolled `fetch` + `ReadableStream` reader (`src/api/chatApi.js`) rather than `EventSource`, since the browser's `EventSource` API can't send a POST body or an `Authorization` header — both of which `/api/ask/stream` requires.

Run it with `npm run dev` (see [Frontend setup](#frontend-setup)); it expects the backend at the URL in `VITE_API_BASE_URL` (`.env`), defaulting to `http://localhost:8000`.

## Known limitations

- Legacy `.doc` and `.xls` files (the old binary Word/Excel formats) aren't parsed — only `.docx`, `.xlsx`, and PDF are supported. Convert to the modern format before uploading.
- `.docx` and `.xlsx` chunks have no page number, since neither format stores pagination in the file (it's computed by the renderer, or doesn't apply to a spreadsheet). Their citations include the document name only.
- **Charts, graphs, and other images are not understood at all** — whether embedded in a PDF, a `.docx`, or an Excel sheet, the pipeline extracts text and table cells only. It never runs OCR or image captioning, so a chart with no underlying text/table data next to it (e.g. a screenshotted graph) is invisible to the chatbot and can't be asked about. Doing this properly would need a vision-capable model (e.g. `ollama pull llama3.2-vision` or `llava`), which isn't wired in — Excel and Word charts that mirror a worksheet/table already in the document are fine, since that underlying data is ingested even though the chart image itself isn't.
- Formula cells in `.xlsx` files are read via their last-cached computed value, not recalculated — a workbook a script generated without ever being opened/saved in Excel or LibreOffice (so it has no cached values) will show those cells as empty.
- The LLM (`llama3.2`, a small 3B local model by default) can misread numbers when reasoning over a table-shaped chunk — e.g. picking the wrong column for "highest Q2 spend." The correct row is retrieved and passed to it correctly (visible in the answer's sources), but arithmetic/tabular reasoning accuracy is limited by the model, not the retrieval pipeline. A larger or more capable Ollama model will do better on these questions.
- No password reset or email verification flow — registration and login only.
- The chat UI renders answers as plain text (no Markdown rendering), even though the LLM may format citations or lists with Markdown syntax.
- The backend's CORS policy is hardcoded to `http://localhost:5173`; deploying the frontend elsewhere requires updating `main.py`.
